## 1. Product intent

**Share what you need to participate—not the private story behind it.**

QuietNeeds helps participants prepare practical event requirements on their own device. Participants edit and explicitly approve each card. Organizers receive only the approved content and use cloud AI to adapt an event. Participants verify whether the changes meet their needs.

Initial audience: organizers and participants in small community workshops. This is a hypothesis to validate, not a claim of demonstrated demand. Winning the hackathon is an aspiration; user value, honest evidence, and reliable execution are controllable goals.

### First demonstration

1. An organizer has planned a photography workshop with a walking session.
2. A participant privately describes difficulty standing and asks for seating.
3. Local AI drafts a practical seated-alternative request, without the personal explanation.
4. The participant reviews and approves the exact text.
5. Cloud AI proposes an alternative using the agenda and approved requirements.
6. The organizer approves a change; the participant confirms its usefulness.
7. Unknown venue facts remain unknown. The app never certifies accessibility without evidence.

### MVP boundary

Include private preparation, sharing preview, organizer workspace, revised-plan confirmation, device readiness, manual fallback, explicit processing status, permissions, and deletion.

Exclude booking, payments, venue search, medical advice, diagnosis, autonomous messages, voice, native mobile apps, vector databases, multi-agent frameworks, and inferred personal profiles. New ideas go into BACKLOG.md; they do not automatically enter the active phase.

## 2. What exists now

This package contains a first **P1 implementation slice**, not a completed hybrid application:

- React/TypeScript participant interface with responsive CSS.
- Private note held only in React memory; no persistence or analytics.
- Firebase AI Logic adapter configured with ONLY_ON_DEVICE.
- Initialization initiated by user click; actual model source checked on response.
- Strict parsing of bounded JSON output; errors do not trigger cloud fallback.
- Manual requirement editing and clearly labeled fictional sample.
- Edits invalidate approval and preview.
- Explicit approval, exact JSON preview, and local JSON download.
- Allowlisted export omits original-note fields and clarification questions.
- Clear-session action; reload discards session content.
- Dependency-free Node tests for the data boundary and adapter configuration.

Verification at packaging: all 6 Node tests passed. Actual dependency installation failed with ENOTFOUND. No production build, browser interaction test, network audit, or real model execution is claimed.

Not implemented: cloud organizer synthesis, authentication, Firestore, invitations, sharing transport, service-worker offline reload, persistent drafts, or deployment. The local adapter is source code awaiting installation, typecheck, configuration, and real-device verification. A static mode check is not a network privacy audit. Model output can still include sensitive text inside a request; human review is mandatory.

## 3. Environment and dependency isolation

### Node is the application runtime

Use Node 22, at least 22.14, and npm. The supplied .nvmrc selects Node 22. Dependencies belong in this project's node_modules, not global installs. package-lock.json must be generated by the first successful install and committed; later installs use npm ci.

NumPy is a Python numerical-computing library, not an environment manager. This application has no Python dependency and does not need a Python virtual environment.

The planned UI UX Pro Max design-search tooling uses Python 3 and its standard library. This is development tooling, not the application runtime. For that tool, create a dedicated environment with `python3 -m venv .venv-design`, activate it with `source .venv-design/bin/activate`, and add .venv-design/ to .gitignore before use. No NumPy or pip dependency is required by the documented search scripts. Run `deactivate` when finished. If Python is unavailable, record the blocker and continue with DESIGN.md; do not add a Python backend.

### Install and run

From a terminal, enter the quietneeds directory containing package.json.

```bash
# If nvm is already installed:
nvm install
nvm use

# Verify Node is 22.14+ on the 22.x line:
node --version
npm --version

# First installation; this generates package-lock.json:
npm install --cache .npm-cache

# Optional until enabling real local AI:
cp .env.example .env.local

# Tests can run even before dependency installation:
npm test

# After installation:
npm run build
npm run dev
```

Open the localhost address printed by Vite in current desktop Chrome. Without Firebase configuration, manual editing and the fixed example are available; real AI remains disabled. Never describe the fixed example as inference.

After a lockfile exists, use `npm ci --cache .npm-cache` for repeatable installation. Commit package.json and package-lock.json together. Do not commit node_modules, .npm-cache, .env.local, logs, or App Check debug tokens.

## 4. Firebase and browser setup

1. Sign into Firebase Console and create/select a dedicated QuietNeeds development project.
2. Register a web app. Copy its public web configuration into .env.local. Do not put a Gemini API secret or service-account credentials in VITE variables: Vite embeds them in browser bundles.
3. Enable Firebase AI Logic with the Gemini Developer API provider through the console workflow.
4. Configure App Check for the web app. The implementation uses ReCaptchaV3Provider. Supply its public site key.
5. For local development only, set VITE_APPCHECK_DEBUG=true. Register the generated token privately in Firebase App Check. Never paste it into project docs, screenshots, public repositories, or submission materials.
6. Verify AI Logic App Check enforcement. Use production attestation before public deployment; debug builds are not production builds.
7. Update desktop Chrome and follow the current Firebase hybrid guide for browser flags and model readiness. Browser/API rollout changes; verify the installed browser, not just a minimum-version claim.
8. Click **Prepare local AI** to initialize/download the model. Download needs internet and sufficient device storage. This step does not receive the private note.
9. Use synthetic text, click **Draft on this device**, and verify an ON_DEVICE response. The adapter rejects any other source.
10. Disconnect the network and repeat in the already-loaded app. Full offline reload is a later P4 task, not an existing capability.
11. Run the privacy network audit below before using real private explanations.

The first slice does not require Authentication, Firestore, or cloud synthesis. Add those during their designated phases.

## 5. Architecture and data contracts

| Boundary | Input | Output | Where it runs |
| --- | --- | --- | --- |
| Private extraction | Private explanation | Unapproved requirements and clarification questions | Device-only Firebase AI Logic |
| Participant review | Unapproved draft | Explicitly approved requirement card | Browser |
| Sharing | Approved card only | Event-scoped stored card | Authenticated Firestore; P2 |
| Organizer adaptation | Approved cards plus supplied event facts | Proposed agenda changes with requirement references | Cloud Firebase AI Logic; P3 |
| Verification | Revised plan and participant feedback | Met / unmet / unknown status | Browser and Firestore; P3 |

Private extraction and cloud adaptation must be separate modules and separate input types. Never pass a full UI state object to a sharing or cloud function. Do not reuse a private-note prompt in a cloud retry path.

First-slice export:

```json
{
  "schemaVersion": 1,
  "requirements": [
    {
      "category": "seating",
      "request": "Please provide a seated alternative to the walking activity."
    }
  ]
}
```

The schema is an allowlist, not an anonymizer. A participant may type sensitive details into request text. Explain this and show all outgoing text. Do not promise anonymity in a small group.

Planned P2/P3 entities: events, joinRequests, members, cards, organizer-only proposals, participant-visible publishedPlans, and confirmations. ARCHITECTURE.md section 5 owns their exact paths and fields, superseding the earlier outline. Keep the P1 local-export schema separate from the revisioned sharing contract.

Rules must deny access by default. Participants can read/write their own cards in events they belong to; organizers can read approved cards for their events; participants cannot enumerate other people's cards. A random invitation URL alone must not authorize arbitrary database access. Design invitation enrollment explicitly during P2.

Withdrawal removes future access where possible but cannot undo an organizer's prior viewing or a downloaded file. Edited or withdrawn cards make dependent plans stale; re-evaluate and reconfirm.

## 7. Plan drift protocol

### Provenance

The user provided [Managing Plan Drift](https://chatgpt.com/share/6af8cf49-7520-83ee-8bed-78efbf35a43c). Its full answer was read in the browser on November 15, 2026 after ordinary web retrieval failed. This supersedes the v1.0 retrieval limitation.

The conversation recommends stable phase IDs, a separate interruption workflow, durable current state, linked issues, checkpoints before complex investigations, explicit return points, isolated branches/worktrees where useful, and verification before resuming. It also distinguishes planning, execution, and enforcement; instruction files alone do not enforce compliance. The following adapts those recommendations to QuietNeeds while keeping existing filenames and completed work.

### Sources of truth

| File | Owns |
| --- | --- |
| QUIETNEEDS_EXECUTION_PLAN.md | Product baseline, stable phases, gates, architecture |
| STATE.md | Current phase/task, evidence, blockers, exact next action |
| BACKLOG.md | Unexpected issues, deferred ideas, parent phase, return point |
| DECISIONS.md | Dated decisions, reasons, alternatives, consequences |
| CHANGELOG.md | Implemented changes and actual verification |
| AGENTS.md | Instructions Codex reads before working |
| CHECKPOINTS.md | Append-only recovery points, evidence, working changes, and return instructions |
| DESIGN.md | Visual language, interaction behavior, screen states, and UX acceptance criteria |
| ARCHITECTURE.md | System boundaries, authoritative schema/access contracts, concurrency and recovery decisions |

Do not copy the live task status into several documents. STATE.md is authoritative for progress; this plan's status table is the creation snapshot.

### Every Codex session

1. Read AGENTS.md, STATE.md, this plan, and open blockers in BACKLOG.md.
2. State the active phase, task, and completion gate in a brief progress update.
3. Check existing files and git changes; preserve user work.
4. Work on the current task. If it is blocked, record why and continue only independent tasks within that phase.
5. Before a complex investigation, write a CHECKPOINTS.md entry and record the exact resume point before switching tasks.
6. Run meaningful checks for changed behavior. Record pass/fail/blocked distinctly.
7. Update STATE.md and CHANGELOG.md before stopping, switching phase, or handing over.
8. Advance only when the gate passes; do not mark external verification complete by assumption.

### Handling unexpected work

- **Blocker:** Prevents current gate. Add issue QN-### with parent task, impact, bounded next action, evidence, and return point. Fix it under the existing phase.
- **Small necessary correction:** Fix within the task and record the change; do not create a new phase.
- **Improvement:** Add to backlog and return to the current task.
- **Scope change:** Record a decision with schedule/privacy impact. Seek user input only for a material product or risk tradeoff, not routine implementation choices.
- **Investigation exceeding 15 minutes without progress:** Write what was tested, what was learned, and the next experiment. Decide whether to continue within scope, take an independent same-phase task, or defer. Do not create new phases or keep expanding the architecture.

### Three control layers from the shared conversation

| Layer | QuietNeeds implementation | Evidence required |
| --- | --- | --- |
| Planning | This versioned plan + DECISIONS.md | Stable phase/task IDs, explicit scope changes and acceptance criteria |
| Execution | STATE.md + BACKLOG.md + CHECKPOINTS.md | Exact task, blocker owner, return point, latest verified checkpoint |
| Enforcement | Tests, eventual Git/PR checks, and optional hooks | Test results and checked diffs, not just an agent saying it followed instructions |

The local project has not yet been initialized as a Git repository. Record commit and branch as null until they actually exist; never invent a last-validated commit. Once Git is set up, keep execution files tracked. For a risky debugging experiment, create a task-specific branch/worktree from a recorded checkpoint rather than mixing speculative changes into the feature. Keep verification as a separate review pass; separate agents are optional, not a prerequisite.

Planned enforcement task P4-T01: add a small plan-state validation script and CI check that validates allowed phase IDs, required state fields, issue-parent references, and checkpoint links. Require review of changes to the phase baseline. This check is planned, not implemented, and cannot prove product correctness or user authorization on its own.

### Interruption-to-resumption procedure

1. Classify the interruption: clarification, minor bug, complex bug, unrelated improvement, architecture change, or blocked dependency.
2. Clarifications and minor bugs stay in the task; record meaningful decisions and run relevant tests.
3. Complex bugs get QN-###, a parent task, owner, and checkpoint before investigation.
4. Unrelated improvements stay in BACKLOG.md. Material scope/architecture changes require an explicit decision; use existing user authorization where it already covers the change.
5. When a blocker is resolved, verify its fix, check the original task's acceptance criteria, and restore the original task to in-progress.
6. Update STATE.md with the exact next action. Close the issue only with evidence. Do not jump ahead to the next phase.

Before resuming after a detour, read the issue's return point and STATE.md. Resolve or defer the issue explicitly; never leave the phase pointer attached to the detour.

## 8. Validation and acceptance

Use synthetic notes only until the privacy audit passes. Build a 30-case evaluation covering timing, seating, sensory needs, cost, uncertain requests, negations, contradictory needs, attempts to override instructions, and sensitive reasons that must not be repeated.

Example: “I need to leave early because I care for someone.” A good draft asks for departure time. It must not invent 4 PM. A blank or unclear input should lead to clarification or manual entry, not confident fabrication.

Proposed gates, not measured results:

- Zero private-note payloads in observed outgoing requests across the test matrix.
- Zero silent changes from pending/uncertain to confirmed in critical test cases.
- All proposed plan changes point to valid approved requirements and supplied facts.
- No access to another participant's card in permission tests.
- No organizer submission before explicit approval; every edit invalidates approval.
- At least three participants and two organizers test the workflow; record disagreements and usability failures honestly.

See TEST_PLAN.md for executable and manual checks.

### Concrete visual direction

Build a calm, premium participation workspace: warm off-white background, deep teal text/actions, restrained sage accents, generous spacing, subtle borders, and strong typography. Use a compact product header and a guided task workspace rather than a marketing hero occupying the main task screen. Avoid decorative gradients, glass panels, stock-photo walls, excessive cards, and constant animation.

DESIGN.md specifies screen layouts, tokens, state behavior, and interaction rules. It is the design source of truth. Codex should inspect the existing code, propose two small layout alternatives in the implementation session, select the clearest one using task completion and accessibility criteria, and record the choice. Optional user aesthetic feedback can refine the direction without blocking independent implementation work.

| Phase | Design work | Completion evidence |
| --- | --- | --- |

### Design acceptance gate

- Responsive at 390, 768, and 1440 px with no horizontal content overflow.
- Keyboard access, visible focus, logical heading order, and labeled form controls.
- Contrast target: WCAG AA; verify actual color pairs instead of assuming the palette passes.
- 44 px minimum target size for primary interactive controls as a project usability target.
- Reduced-motion preference respected; no animation is necessary to understand status.
- No fake AI progress, false saved indicators, or false sharing confirmations.
- Human-readable preview contains all outgoing user-authored content, with technical JSON as an optional disclosure.
- Every edit invalidates consent; preserve that behavior during component refactors.
- Device unavailable, download, inference failure, empty, loading, and success states all have clear next actions.
- No actual private text in screenshots, browser traces, design tools, or skill prompts.
